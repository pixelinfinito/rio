# Design

## Context

See proposal.md for motivation. The v0.2 system this design extends:

- The CLI builds the whole submission (snapshot, changed files, deterministic report, both graphs, owner guidance, intent) and `POST /v1/reviews` validates it against the immutable snapshot. The Worker never reads a repository itself.
- The Workflow runs steps from the resolved profile; `rio/agents` and `rio/security` dispatch agents by name through one generic prompt and tool set; agent manifests under `modules/agents/` carry only `run`, `available` and `independent`. The security branch today sets the report `partial` with an "unavailable until v0.3" note.
- The convergence change stores lineages keyed by `(tenant, repository, kind, ref)`, a `findings` table keyed by lineage generation and identity with lifecycle `status`, a `feedback` table with the five reasons, and `posted_json` on the lineage for "never re-post". Its PR-thread behaviors are specified there and only need a host.
- Runners (self-hosted Docker, Cloudflare Sandbox) execute `run`, `checks`, `graph` and `static` job kinds against a streamed snapshot archive with `network: false`, authenticated by job-scoped capability tokens.
- Report formats are `terminal`, `json` and `md`, rendered by `rio-core`; the Worker stores the JSON report and the CLI renders it.
- Tokens are bearer tokens with scopes (`reviews:write`, …) in `api_tokens`, or the owner token.

Constraints:

- Finding identity, evidence rules and the "agreement is not evidence" rule from v0.1 and v0.2 are unchanged.
- Policy comes only from the resolved profile; webhook payloads, PR descriptions and comments are data.
- Source code leaves the account only to the configured model provider. GitHub receives comments, check runs and metadata, never snapshots.
- Fork PRs are static-only and never publish automatically (TRD security model).
- v1 schemas are extended with optional keys only.

## Goals / Non-Goals

**Goals:**

- A PR opened against a repository with the app installed is reviewed and, under `publish: auto`, annotated without anyone running a command, with the same report the CLI would produce.
- Every publication is idempotent: re-running a round edits, never duplicates, even after a failed or interrupted publication.
- Findings, dismissals and suppression proposals are repository-level facts that outlive one PR.
- SARIF consumers (GitHub code scanning, IDEs) see the same findings with the same identities as the terminal.
- The contracts and security agents are specified tightly enough that their hypotheses can be evaluated against the reference set like the correctness agent's.

**Non-Goals:**

- GitLab, Bitbucket or Gitea: the webhook route stays reserved; the publisher is written behind a host interface but only GitHub is implemented.
- Merge blocking (R23): the check run is always neutral.
- Auto-applying suppressions or editing repository files from the endpoint.
- Caching verifier results: verification is always fresh.
- Council and QA behavior (sibling changes).

## Decisions

### D1. GitHub App via manifest, installation per repository, tokens per job

`rio init` offers "Register a GitHub App" after the provider step. It opens the GitHub App manifest flow with a manifest that declares exactly `contents: write` (only the token that resolves finding threads uses write, because GitHub requires it for `resolveReviewThread`), `pull_requests: write`, `checks: write`, `metadata: read`, `members: read` (for actor classification), `issues: read` (GitHub requires it for the `issue_comment` event) and the webhook URL `https://<worker>/v1/hooks/github`; GitHub returns the app id, private key, webhook secret and client credentials, which the CLI stores as Worker secrets (`GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET`) and never writes to disk unencrypted. `installation` webhook events record `(installation_id, account, repositories[])` in a new `installations` table. The Worker mints a GitHub App JWT and exchanges it for an installation token scoped to one repository with the permissions a job needs: `contents: read` for a prepare job, `pull_requests: write` plus `checks: write` for publication. Tokens live at most ten minutes, are passed to a runner inside the job payload and never persisted. Alternative: a personal access token entered at `rio init`. Rejected because it acts as a user, cannot be scoped per repository and is not revocable per installation. Alternative: OAuth app. Rejected because it cannot post check runs or receive webhooks as itself.

### D2. Webhook ingestion is verified, deduplicated and queued

`POST /v1/hooks/github` requires a valid `X-Hub-Signature-256` over the raw body with the webhook secret, a `X-GitHub-Delivery` id not seen in the last 24 hours (table `deliveries`), and an installation that exists in `installations`. Accepted events: `pull_request` with actions `opened`, `synchronize`, `reopened`, `ready_for_review`; `issue_comment` `created` on a PR whose body starts with `/rio`; `installation` and `installation_repositories` for registry maintenance; everything else returns 204 and is ignored. A `pull_request` event enqueues a `review-request` message (repository, PR number, base and head SHAs, fork flag, author login and type, installation id) on the existing queue; the consumer creates the review and the prepare job. Draft PRs are ignored until `ready_for_review`. The HTTP handler never calls GitHub or the model gateway, so GitHub's 10 s delivery timeout is always met. Alternative: process synchronously in the handler. Rejected for the timeout and because retries would duplicate work.

### D3. Hosted preparation is a runner job that runs the same `rio` binary

A PR review needs the submission the CLI would have built. A new runner job kind `prepare` receives `{ clone_url, base_sha, head_sha, installation_token, repository, lineage, fork, pr }` and runs, inside the job's container, `rio prepare --base <sha> --head <sha> --submit` from the paired `rio` binary shipped in the runner image: clone with the token (the only phase with network), check out head, build the snapshot, run deterministic checks and the graph, write owner guidance and intent input, upload the snapshot through the existing content-addressed protocol with the job's capability token, and `POST /v1/reviews` with the job's token. The network is removed before checks run (Docker: a second container stage on the pod-less `none` network with the clone bind-mounted; Sandbox: fetch and analysis as two steps where the second has no egress). Deterministic checks follow the existing skip rules of local reviews: a check whose dependencies are not installed in the clone, or cannot be verified against the lockfile, ends `skipped: dependency_mismatch` with a hint, a check whose tool is absent ends `skipped: tool_missing`, and the dependency audit, which needs its advisory service, ends `skipped: offline` because the analysis has no network; the footer reports each; the runner image ships the TypeScript, Python and Rust toolchains so typecheck and lint run when the project vendors or locks its dependencies in a way the existing compatibility check accepts. Fork PRs prepare the same way but the submission carries `fork: true`, so agents and voters run static-only and nothing publishes. The Sandbox backend prepares non-fork PRs only; the self-hosted runner prepares any. Alternative: implement prepare in TypeScript in the Worker from the GitHub contents API. Rejected: the deterministic checks and graph are Rust, the Worker has no process model for tools, and the CLI and PR paths would drift. Alternative: require the author to run `rio review --pr`. Rejected because it is not PR mode.

### D4. `rio review --pr <n>` reuses hosted preparation

With an endpoint and an installation covering the repository, `rio review --pr 123` asks the endpoint to prepare and review the PR as a `pr` lineage and waits on the same event stream as a local review; nothing is built locally, so the result is identical to the webhook path and the author's working tree is irrelevant. `--publish` is the `ask` consent for that review. Without an endpoint, exit 2 as today; with an endpoint but no installation for the repository's `origin`, exit 2 naming `rio init` and the GitHub App step. Alternative: fetch the PR refs locally and submit as before. Rejected because it would review the author's checkout of the PR, not the PR, and would make `--pr` behave differently from the webhook.

### D5. Publisher: review comments with markers, one summary, one check run

Publication is a Workflow step after `rio/report` with a host interface (`post`, `edit`, `resolve`, `check`) and a GitHub implementation. For each publishable finding (after convergence's hold-back and cap rules) whose primary location is on a line present in the PR diff, the publisher creates a pull request review comment (`commit_id` = head SHA, `path`, `line`, `side: RIGHT`) whose body ends with `<!-- rio:finding:<identity> -->`; findings that GitHub cannot anchor (pre-existing lines, deleted files, class findings with many locations) are listed in the summary. Exactly one summary issue comment per lineage, marked `<!-- rio:summary:<lineage-id> -->`, carries the status, risk tier, counts, held-back and remembered counts, the reconsider message at the cap, and the deep link to the report. A `rio/review` check run on the head SHA is created or updated with `conclusion: neutral` and a summary; it never uses `failure` or `success`. Comment ids are stored in the lineage's `posted_json` and in a `publications` table with per-finding state (`posted`, `edited`, `resolved`, `failed`); before any post the publisher reconciles against GitHub by searching the PR's comments for the marker, so a lost record never duplicates. Edits use `PATCH`; thread resolution uses the GraphQL `resolveReviewThread` mutation with the thread id fetched once per PR. Alternative: one review submission with all comments (`POST /pulls/{n}/reviews`). Rejected: GitHub assigns comment ids only after submission and rejects the whole review if one anchor is invalid, which defeats per-finding idempotency. Alternative: issue comments only. Rejected because inline anchoring is the point of PR review.

### D6. Publish policy semantics

`publish: never` posts nothing, not even the check run. `publish: auto` posts everything from webhook and CLI reviews. `publish: ask` posts from the CLI only when the user confirms the prompt or passed `--publish`; webhook-triggered reviews under `ask` post the check run only, with its summary stating that publication requires `publish: auto` or `rio review --pr <n> --publish`, so the team sees that Rio ran without comments appearing unasked. Fork PRs post nothing until a maintainer comments `/rio review`, which escalates the lineage per the convergence change and publishes under the profile policy; forks never get `run` tools even after escalation (TRD). Alternative: treat `ask` as `auto` on webhooks. Rejected: a default profile that silently comments on every PR is the behavior teams uninstall.

### D7. Actor classification and commands

`/rio` commands are parsed from `issue_comment` bodies on PRs only; the actor's permission comes from `GET /repos/{owner}/{repo}/collaborators/{user}/permission` through the installation token, never from the payload. `admin` and `maintain` are maintainers; `write` and `triage` are collaborators; everything else is other. `/rio review` from a maintainer resets the lineage (convergence D1) and escalates a fork PR; from anyone else it is acknowledged with a reaction and ignored. `/rio dismiss <id> <reason>` from a collaborator or maintainer writes `author_response` through the same code path as `POST /v1/findings/{id}/feedback` with `actor` = login; the `<id>` may be the full identity or an unambiguous prefix of at least eight characters; the bot reacts to the comment and edits the finding's comment to show `dismissed: <reason>`. Commands from the app itself and from other bots are ignored. Results are posted as reactions and comment edits, not new comments, so command traffic cannot create noise.

### D8. Finding history is a repository registry

A `finding_history` table keyed by `(tenant, repository, identity)` records `first_seen_review`, `last_seen_review`, `seen_count`, the latest lifecycle `status`, `author_response_json`, the last location and `code_hash`: the hash of the normalized enclosing-symbol text at the head where the status was last set. It is updated from every finished review, lineage or not. During consolidation the registry is consulted: a finding whose identity is `dismissed` with reason `intentional`, `irrelevant` or `style` and whose current `code_hash` equals the recorded one is removed from the main sections and counted in the footer as remembered with its reason and the PR or review that dismissed it; if the code changed, it is reported again with `history` showing the earlier dismissal. `wrong` is never remembered as a suppression: the finding is reported again when it reproduces, carrying the earlier `wrong` so the reader and the evaluation harness see the recurrence. `fixed` findings that reappear are reported as regressions of a fixed finding. finding-v1 gains optional `history: { first_seen, last_seen, seen_count, previous_status, previous_response, dismissed_in }`. `GET /v1/findings?repository=&status=&rule=` lists the registry; `rio findings [--status …] [--rule …]` renders it. Alternative: extend lineage `findings` rows. Rejected: lineages are per PR and the registry must survive them. Alternative: let the registry suppress `wrong` as well. Rejected because an identity dismissed as wrong once is exactly the finding whose recurrence must be visible to measure the false-positive rate.

### D9. SARIF 2.1.0 mapping shared by Rust and TypeScript

The CLI renders SARIF in `rio-core` and the Worker renders it in TypeScript for `GET …/report?format=sarif`; both implement `docs/sarif-mapping.md` and are tested against the same fixtures (`tests/fixtures/sarif/<case>/{report.json,expected.sarif}`), so the two outputs are byte-identical after key ordering. Mapping: one `run` per review; `tool.driver` is `rio` with the CLI or endpoint version and `rules[]` built from the distinct `rule_id` values with `shortDescription` from the first message and `properties.category`; one `result` per finding occurrence group, `ruleId` = `rule_id`, `level`: `error` for severity `error`, `warning` for `warning`, `note` for `info` and for every `risk` or plausible entry; `message.text` = message plus trigger; `locations[]` = every location with `physicalLocation.artifactLocation.uri` (repository-relative, `uriBaseId: SRCROOT`) and `region`; `partialFingerprints.rioFindingId/v1` = identity; `baselineState` = `new` for `new` and `worsened`, `unchanged` for `pre-existing`, `absent` for `fixed`, omitted for `unclassified`; `properties` = `evidence_level`, `category`, `state`, `status`, `severity`, `verification`, `round`, `author_response`, `history`; run `properties` = `rio.status`, `rio.risk_tier`, `rio.lineage`, `rio.review_id`; `invocations[0]` = `executionSuccessful` (status not `error`), `exitCode`, `startTimeUtc`, `endTimeUtc`; `originalUriBaseIds.SRCROOT` = repository root. Refuted hypotheses, suppressed and remembered findings, category-floor drops and `pre-existing` findings not shown in the main sections are omitted; `incomplete` checks become `invocations[0].toolExecutionNotifications` with level `warning`. Alternative: emit SARIF from JSON on the client only. Rejected because CI consumers fetch from the endpoint without a CLI.

### D10. Suppression proposals need evidence and a human

A proposal is computed when a review finishes, per repository, from `feedback` rows of the last 90 days: at least `proposal_threshold` (default 3) dismissals with reason `irrelevant` or `style` on the same `rule_id` yield a `{ rule }` proposal; the same count on findings under one directory with mixed rules yields a `{ path: <dir>/** }` proposal; `wrong`, `fixed` and `intentional` never count (wrong is calibration, fixed is success, intentional is per instance). Proposals live in `suppressions` with `origin: proposed`, `status: proposed | applied | declined`, the evidence (finding ids, reasons, actors, dates) and an id. The report footer lists open proposals for the repository with their evidence counts; `rio suppressions list` shows them; `rio suppressions apply <id>` prints the YAML entry and the evidence, asks for confirmation (or `--yes`), appends the entry to the repository's default profile file (creating `.rio/profiles/default.yaml` extending `rio/base` if absent), validates the profile, and marks the proposal `applied` on the endpoint; `rio suppressions decline <id> [--note]` marks it `declined` so it is not re-proposed for 180 days. The endpoint never writes repository files and never applies a suppression to a review by itself. Alternative: endpoint-side suppressions applied automatically after threshold. Rejected: the PRD requires confirmation, and a suppression is policy, which only the profile may carry.

### D11. Agent result cache is keyed by hunk and context, replays hypotheses, never verification

For each agent and each changed hunk the agents step computes `hunk_hash = blake3(path | normalized hunk text)` and `context_hash = blake3(agent | manifest version | prompt hash | model identifier | resolved agent options | base and head content hashes of the enclosing symbols and their one-hop graph neighbors | owner guidance hashes in scope)`. The object `cache/<hunk_hash>/<context_hash>.json` holds the agent's hypotheses for that hunk with their source; an index row `(tenant, hunk_hash, context_hash, created_at, last_hit)` supports retention. On a hit the hypotheses are replayed with `source.cached: true` and no model call is made; the verifier always runs on them. Cache objects are per tenant (the key is prefixed with the tenant), skipped for fork PRs (their static-only hypotheses would poison non-fork reviews) and when the `rio/agents` step sets `cache: false`, and expire with the repository's evidence retention (default 90 days). `report.cache = { lookups, hits, hit_rate, tokens_saved_estimate }` feeds the footer. The whole-agent output is sliced per hunk by the hypothesis location, so an agent reviewing several hunks fills several entries. Alternative: cache per review (whole submission). Rejected: nothing matches across PRs. Alternative: also cache verification. Rejected: a reproduction is evidence only when it ran against this head.

### D12. Contracts agent

`modules/agents/contracts/` gains `prompt.md`, and the manifest declares `contracts: true` so triage's `public_contracts` signal selects it. The step gives it, besides the generic inputs, a contract inventory computed deterministically from the graph and adapters: nodes of kind `endpoint`, `table`, `event`, `config` and exported symbols (adapter-declared visibility: TypeScript `export`, Python names without a leading underscore in `__all__` or module scope, Rust `pub` reachable from the crate root) that changed between base and head, with their consumers at `hops` in both versions. The agent emits hypotheses in the `contracts/<kind>/<break>` rule namespace (`signature`, `route`, `schema`, `migration`, `format`, `cli`, `env`, `config` × `removed`, `changed`, `added_required`, `semantics`), each with at least two `locations` (producer and one consumer) or the explicit statement that no consumer exists in the repository, in which case the hypothesis is `risk` not `defect`. `run: false` by default; the verifier settles contract hypotheses statically through graph paths. Alternative: fold contracts into the correctness agent. Rejected: the correctness agent reasons from the change outward; contracts reasons from consumers inward, and the PRD lists them separately so their precision is measured separately.

### D13. Security agent with catalog modules

`modules/catalogs/owasp-top10-2025.yaml` and `asvs-5.0.yaml` are a new module kind `catalog` (module-v1 gains it): items with `id` (`A01:2025`…, `V2.1.1`…), `title`, `summary` written for this project, `applies_when` predicates over languages, frameworks detected by prepare, and touched node kinds (`endpoint`, `table`, `config`, `auth` paths from `sensitive_paths`), and `trace` hints (which taint sources and sinks matter). The security step resolves the profile's `catalog`, filters items by `applies_when` against the change, and gives the agent the applicable items, the generic inputs and a taint model: input → validation → authorization → transformation → sensitive operation, traced along the graph in both versions. Each hypothesis carries `catalog_item` and category `security`; the agent returns `unassessed: [{ item, reason: budget | no_evidence | tools_unavailable }]` for applicable items it could not conclude on, which the report's security section and footer list, so "nothing found" is never confused with "nothing checked". `run: true` by default (fork: off). The manifest becomes `available: true`; the v0.2 unavailable note is removed; `modules/profiles/security.yaml` extends `rio/base` with security `enabled: true`, `posture: thorough`, catalog `asvs-5.0` and the council step from the sibling change left disabled until that change lands. Alternative: embed the catalogs in the prompt. Rejected: catalogs are data that teams extend (`catalog: .rio/catalogs/internal.yaml` is a natural later step) and their applicability is deterministic.

### D14. Release gate for the v0.3 exit criterion

`eval/gate.py` gains `--false-positive-rate`: for each agent, `wrong / (fixed + wrong + intentional + irrelevant + style)` over posted agent findings on the reference set and the adjudicated noise runs, failing when any agent with at least 30 responses exceeds 15 %. The release checklist for v0.3 lists it next to the council keep-or-remove rule. Agents under the sample floor are reported, not gated.

## Risks / Trade-offs

- [Installation tokens reach a runner] → tokens are minted per job with `contents: read` on one repository, live ten minutes, are passed in the job payload only, and the clone phase is the only networked phase; self-hosted runners already receive snapshot content, so a token adds read access to what they already have.
- [Webhook replay or forgery] → signature over the raw body, delivery id deduplication, installation lookup, and handlers that do no privileged work synchronously.
- [GitHub rejects an inline anchor] → fall back to the summary for that finding, record the failure per finding, retry on the next round; the marker reconciliation prevents duplicates.
- [Partial publication after a Worker error] → `publications` rows plus marker search make publication idempotent; the step is re-run safely.
- [Hosted checks skip for lack of dependencies] → reported as skipped with the reason and the hint to vendor or lock dependencies; agents, graph, secrets and dependency audit still run; same rule the CLI applies.
- [Remembered dismissals hide a defect whose context changed but whose symbol text did not] → `code_hash` covers the enclosing symbol; `wrong` is never remembered; the footer lists every remembered identity with a one-flag override (`--show-remembered`) and the registry is queryable.
- [SARIF consumers treat `note` risks as noise] → risks carry `properties.category: risk` and a message prefix; consumers can filter by level.
- [Suppression proposals nudge teams into silencing rules] → proposals need repeated `irrelevant`/`style` reasons, never `wrong`; evidence is shown; application is a confirmed local edit that goes through code review like any profile change.
- [Cache returns stale hypotheses after a prompt or model change] → both are in the context hash; manifest version bumps on prompt edits are enforced by a test that hashes `prompt.md`.
- [Catalog items paraphrase OWASP material] → items carry the official id and a link; summaries are Rio's own text; the files carry the CC BY-SA attribution OWASP requires.
- [Contracts agent floods with `added_required` on every new parameter] → hypotheses without a consumer location are risks, and the posture cap applies; precision per agent is measured and gated.

## Migration Plan

Additive. D1 migration `0004_pr_mode.sql` adds `installations`, `deliveries`, `publications`, `finding_history`, `suppressions` and `agent_cache`; `rio deploy` applies it. Worker secrets for the GitHub App are optional: without them the webhook route returns 404 and `--pr` exits 2 with the installation hint. finding-v1 gains `history`; report-v1 gains `publication`, `cache` and `suppression_proposals`; module-v1 gains kind `catalog`; profile-v1 adds the `rio/agents` `cache` option. The security manifest flips `available` to true in the same release as the catalogs; profiles that enabled security in v0.2 start running it, which the release notes state. Rollback: redeploy the previous Worker; the new tables are unused and harmless.

## Open Questions

- Whether `rio review --pr` should also accept a PR URL (`https://github.com/o/r/pull/123`) in addition to a number; the number form is specified and the URL form can be added without changing behavior.
- Whether the GitLab publisher reuses the same marker format (likely yes; GitLab discussions support HTML comments) — decided when that change is written.
- Whether `finding_history` should expire rows for repositories with no review in a year; retention for findings is indefinite in the TRD and nothing here depends on the answer.
