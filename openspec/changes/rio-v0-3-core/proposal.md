# Proposal

## Why

v0.2 ships a reviewer that only its author can run: the CLI submits a snapshot, the endpoint reviews it, the terminal shows the result, and nothing reaches the pull request, the security step reports itself unavailable, the contracts agent has no specification, and findings are forgotten once their lineage ends. The PRD's v0.3 row ("Contracts agent; security step; PR mode with GitHub App applying the convergence rules to threads; finding state across runs; SARIF; feedback with standardized reasons; council step for selected findings; noise measurement and incident import") is the release that makes Rio usable by a team instead of one developer. This change specifies the parts of that row that no other change owns: the GitHub App and PR mode (R14), finding history across runs (R15), SARIF (R16), suppression proposals from feedback (R17), the agent result cache (R18), the contracts and security agents with their catalogs (R13, R29). The council (R30) stays in `rio-v0-3-council`; convergence, standardized reasons, noise and incidents (R27, R28, R31) are in `rio-v0-2-review-convergence`; the QA engine is `rio-v0-3-qa`.

**Scope assumption.** This change depends on the v0.2 endpoint, verifier quorum, self-hosted runner and hosted snapshot protocol, and on the convergence change's lineages, `findings` table, lifecycle `status` and feedback endpoint. PR-thread behaviors that the convergence change already specifies (never re-post, edit in place, the reconsider message, `/rio dismiss`, maintainer `/rio review` reset, auto-resolution conditions) are consumed here, not re-specified; this change specifies the host mechanics that make them possible. GitHub is the only host in v0.3; GitLab keeps its webhook route reserved and follows the same design later (PRD open question). The council change's `nightly` and `verify.split` predicates and its vendor governance are not touched. The exit criterion "false positives per agent < 15 %" is measured with the `wrong` reason aggregation the convergence change adds, and this change adds the release gate that reads it.

## What Changes

- **GitHub App integration.** `rio init` gains an optional step that registers a GitHub App from a manifest with read-code and write-PR-comment permissions only, stores the app id, private key and webhook secret as Worker secrets, and records the installation. The Worker verifies `POST /v1/hooks/github` signatures, handles `pull_request` (opened, synchronize, reopened, ready_for_review) and `issue_comment` (`/rio review`, `/rio dismiss <id> <reason>`) events, classifies the actor (maintainer, collaborator, other) from the installation's permission API, and flags fork PRs. Installation tokens are minted per job, scoped to one repository, and never stored.
- **Hosted preparation.** A PR review has no CLI to build its submission, so the Worker schedules a `prepare` runner job that clones base and head with a short-lived installation token, builds the content-addressed snapshot, runs deterministic checks and the graph with the same `rio` binary the CLI uses, and uploads the submission that `POST /v1/reviews` already accepts. Fork PRs prepare with network only for the clone and run static-only afterwards; the Cloudflare Sandbox backend may prepare non-fork PRs, the self-hosted runner may prepare any.
- **`rio review --pr <n>` from the CLI.** The CLI resolves the PR through the endpoint, reviews the PR head as a `pr` lineage, and `--publish` posts the result; the v0.1 rule that these flags exit 2 is replaced by "exit 2 without an endpoint or without an installation".
- **PR publishing.** One publisher applies the profile's `publish` policy (`never`, `ask`, `auto`), posts inline review comments on diff lines that the PR can anchor, falls back to the summary comment for the rest, embeds a hidden identity marker in every comment so later rounds edit rather than duplicate, posts exactly one summary comment per lineage, and creates a neutral `rio/review` check run carrying the status, risk tier and counts; the check run never blocks and never approves. Dismissals and fixes resolve the review thread with the reason. Publication for fork PRs needs a maintainer `/rio review`.
- **Finding history across runs.** A per-repository registry keyed by finding identity remembers every finding's first and last review, lifecycle status and author response across lineages. A finding dismissed `intentional`, `irrelevant` or `style` on unchanged code stays dismissed in later reviews of the same repository and is rendered in the footer as remembered rather than re-reported; `wrong` dismissals are remembered as calibration evidence but the finding is re-reported if it reproduces after the code changed. `GET /v1/findings` lists the registry; `rio findings` shows it; finding-v1 gains an optional `history` block.
- **SARIF output.** `--format sarif` and `GET /v1/reviews/{id}/report?format=sarif` emit a SARIF 2.1.0 log: one run per review, rules from `rule_id`, results with `level` from severity, `partialFingerprints` from the finding identity, `baselineState` from regression state, every location, evidence level, category, lifecycle status and verification metadata in `properties`, the risk tier and status in run properties, and an invocation record with the exit code. Plausible risks are `note` level results flagged as risks; refuted and suppressed findings are absent.
- **Suppression proposals.** When a repository accumulates dismissals of one rule or path with reasons `irrelevant` or `style` beyond a threshold, the endpoint records a proposed suppression (origin `proposed`), the report footer and `rio suppressions list` show it with its evidence, and `rio suppressions apply <id>` writes the entry to `.rio/profiles/default.yaml` only after explicit confirmation. Nothing is suppressed automatically; `wrong` dismissals never propose a suppression.
- **Agent result cache.** Agent hypotheses are cached in R2 under `cache/<hunk_hash>/<context_hash>.json`, keyed by the hunk's content and a context hash over the symbol slice both versions, the agent's manifest version, prompt hash, model identifier and resolved agent options. A hit replays the hypotheses into the verifier without a model call; the footer reports the hit rate; entries expire with the repository's retention and are never used across tenants or on fork PRs.
- **Contracts agent.** `rio/agent-contracts` becomes a specified agent: it identifies public contracts touched by the change (exported signatures, HTTP routes and schemas, database migrations, serialized formats, CLI flags, environment variables, configuration keys), traces their consumers through the graph in both versions, and emits hypotheses about compatibility breaks, missing migrations and unmet consumer assumptions, each citing the producer and a consumer. Triage's `public_contracts` signal selects it.
- **Security agent and catalogs.** `rio/agent-security` becomes available: it reviews with the resolved catalog (`owasp-top10-2025` or `asvs-5.0`) as a checklist shipped under `modules/catalogs/`, traces input → validation → authorization → transformation → sensitive operation along the graph, emits `security` hypotheses with the catalog item id, and reports the catalog items it could not assess. The `security` community profile enables it with `posture: thorough`; `rio/base` keeps it disabled. The v0.2 "unavailable" note disappears.
- **Release gate.** The release checklist gains the v0.3 exit criterion: false positives per agent below 15 % from `wrong` responses on the reference set, computed by `eval/` from the convergence change's aggregation.

Nothing is breaking. finding-v1 gains the optional `history` block; report-v1 gains optional `publication`, `cache` and `suppression_proposals` objects; profile-v1's existing `publish` key gains its semantics and `rio/agents` gains the `cache` option; module-v1 is unchanged. New wire contracts: the GitHub webhook payload subset the Worker accepts, the `prepare` job, `GET /v1/findings`, `GET/POST /v1/suppressions`, and `POST /v1/reviews/{id}/publish` (reserved in the TRD).

## Capabilities

### New Capabilities
- `git-host-integration`: GitHub App registration and secrets, installation tokens, webhook verification and events, actor classification, fork detection, PR metadata, hosted preparation of a PR review, and the GitLab reservation.
- `pr-publishing`: the publish policy, inline and summary comments with identity markers, editing, thread resolution, the check run, `/rio` command handling, fork publication rules, and the publication record in the report.
- `finding-history`: the per-repository finding registry, remembered dismissals, re-reporting rules, `GET /v1/findings`, `rio findings` and the `history` block.
- `sarif-output`: the SARIF 2.1.0 mapping, format selection in the CLI and API, and what is excluded.
- `suppression-proposals`: proposal thresholds and evidence, storage, listing, explicit application to the profile, and the rule that nothing is suppressed automatically.
- `agent-result-cache`: cache key, hit and miss behavior, invalidation, tenancy, fork exclusion, metrics and retention.
- `contracts-agent`: contract detection, consumer tracing, hypothesis content, triage selection and the fork and budget rules.
- `security-agent`: catalog modules, the taint trace, hypothesis content with catalog ids, unassessed-item reporting, and the community profile.

### Modified Capabilities
- `security-step`: staged availability becomes v0.3 availability; the unavailable note is replaced by the agent's unassessed-item report.
- `review-profiles`: `publish` semantics, the `rio/agents` `cache` option, the `security` community profile, and validation of a suppression entry written by `rio suppressions apply`.
- `findings`: the optional `history` block and the remembered-dismissal rule in suppression application.
- `review-report`: the `sarif` format, and the `publication`, `cache` and `suppression_proposals` report objects with their footer lines.
- `cli/review`: `--pr`, `--publish` and `--format sarif` become supported with an endpoint; exit codes for missing installation and publication failure.
- `cli/doctor`: GitHub App diagnostics and `--rotate` for the webhook secret.

## Impact

- **Code**: `worker/` (webhook route and signature check, installation token minting, event handlers, `prepare` job scheduling, publisher with GitHub REST and check-run calls, finding registry, suppression proposals, agent cache, SARIF renderer shared with `rio-core` through the generated validators), `rio-runner` (the `prepare` job kind: clone, snapshot, checks, graph, upload), `rio-cli` (`--pr`, `--publish`, `--format sarif`, `rio findings`, `rio suppressions`, `rio init` GitHub App step, `rio doctor` lines and `--rotate`), `rio-core` (SARIF renderer, `history` block, new report objects and footer lines), `rio-profile` (`publish` consumption, `cache` option, community profile), `modules/agents/contracts` and `modules/agents/security` (prompts, manifests, `available: true`), new `modules/catalogs/owasp-top10-2025.yaml` and `asvs-5.0.yaml`, `modules/profiles/security.yaml`, `eval/` (false-positive gate, cache hit accounting), D1 migration `0004_pr_mode.sql` (`installations`, `finding_history`, `suppressions`, `publications`, `agent_cache` index).
- **Contracts**: finding-v1 `history`; report-v1 `publication`, `cache`, `suppression_proposals`; profile-v1 `publish` semantics and the `rio/agents` `cache` option; `schemas/sarif-mapping-v1.md` documents the mapping; `docs/github-app.md` documents installation and permissions. All additive.
- **Network and data**: the Worker calls `api.github.com` with installation tokens for metadata, comments and check runs; runners clone from GitHub with a token valid for minutes and scoped to one repository; no repository secrets are read. Source code still leaves the account only to the configured model provider.
- **Security**: webhook signatures and replay windows; actor classification from GitHub, never from the payload text; fork PRs static-only and unpublished until a maintainer asks; comment bodies are data and cannot change policy; the app's permissions are the minimum the manifest declares.
- **Cost**: PR mode adds one `prepare` job per review round; the agent cache removes repeated model calls on unchanged hunks across rounds and PRs, shown as a hit rate.
