## Why

Rio does not exist yet: the repository holds only a PRD and a TRD. The PRD's release plan makes v0.1 a local-only CLI whose deterministic layer must prove useful on its own in 10 real PRs before any backend, agent or verifier work starts. This change establishes that foundation: the Cargo workspace, the review model, the profile engine, the TypeScript, Python and Rust adapters, the lazy impact graph and the terminal report, all running on the developer's machine with no endpoint. Rust is in from the start so Rio can review its own codebase from day one.

**Scope assumption.** The PRD and TRD describe the whole product through v1.0. One change cannot carry that, so this change is scoped to the PRD's v0.1 row. Everything that needs a model, a Cloudflare endpoint, a runner or a git host (intent inference, agents, verifier, `rio init`, PR mode, publishing, `--since-last`, feedback) is explicitly out of scope and will come as later changes. Where v0.1 needs a piece of a later feature (for example the profile schema), this change builds the piece to the TRD contract so later changes extend rather than replace it.

## What Changes

- **New Cargo workspace** `crates/` with `rio-cli`, `rio-core`, `rio-git`, `rio-profile`, `rio-adapters`, `rio-graph`, plus `modules/` (built-in `rio/*` modules and the `rio/base` profile) and `schemas/` (`profile-v1.json`, `module-v1.json`, `finding-v1.json`). `rio-client` and `rio-runner` are stubbed as empty crates to fix the workspace layout but carry no behavior.
- **`rio review`** reviews working-tree, staged, or `--base <ref>` changes with no endpoint configured. `--pr`, `--deep`, `--publish`, `--since-last` are parsed but exit with an actionable "requires an endpoint (v0.2)" message. `--offline` is accepted and disables the only network call Rio itself makes (OSV); tool and test processes are not network-isolated in v0.1, and the footer says so.
- **Change resolution and snapshots**: base/head resolution, unified diff with hunk line ranges, and a BLAKE3 content-addressed snapshot of changed files plus base SHA, so every run is pinned to immutable versions.
- **Profile engine (local subset)**: YAML profile schema v1, single inheritance via `extends` with deep-merge and list override, JSON-schema validation, module reference resolution for built-in `rio/*` modules, `suppress` and `fail_on` policies, and the non-overridable guardrails (verifier always present, `min_evidence` never below `plausible`). The schema also carries four keys that later releases consume and that must exist in v1 so profiles written now stay valid: `posture` (`critical-only | balanced | thorough`, which jointly derives `min_evidence`, `max_defects`, the defect severity floor and whether `plausible` risks render), `max_defects` (default 5), `rounds: { cap, diff_only_after }` and `always_human: [globs]`. v0.1 validates them, resolves posture into its derived values in `profile.resolved.yaml`, and applies only `always_human` (as a `risk_tier` of `high` in the report); `max_defects` never caps deterministic findings. Steps whose module cannot run locally (agents, verifier, prepare's intent agent) are validated but not executed, and are listed in the report footer. Triage rule *syntax* is validated; rule *evaluation* that selects agents is deferred to v0.2.
- **`rio profile list|show|validate`** against repo (`.rio/profiles/`), personal (`~/.config/rio/profiles/`) and built-in profiles.
- **Language adapters** for TypeScript, Python and Rust behind one `Adapter` trait with declared capabilities (`parse`, `typecheck`, `lint`, `test`, `coverage`, `scan`) and repository detection from manifests and config files. The Rust adapter is workspace-aware: `cargo check` and `cargo clippy` with `--message-format=json` (clippy only when the project configures it), `cargo fmt --check` as a formatting diagnostic group, `cargo llvm-cov` for diff coverage when installed, a `Cargo.lock` v3/v4 parser feeding the dependency audit with `crates.io` as the OSV ecosystem, and Tree-sitter Rust queries for the graph. `target/` is linked into disposable tool trees like `node_modules`; Rio never runs `cargo build` for the user.
- **Deterministic checks**: compile/type errors, lint groups (only when a project lint config exists), secrets, diff coverage (`untested_change`), dependency vulnerabilities via OSV (`vulnerable_dependency`). Checks that can run on both versions (typecheck, lint) classify each occurrence as new, pre-existing or fixed before grouping, so old issues are separated from regressions and an extra occurrence of an existing problem is reported as `worsened`. Every check run ends in an explicit outcome (`passed`, `findings`, `failed`, `skipped`, `cancelled`). A missing tool is a visible `skipped` entry, never silence, and a crashed or cancelled check makes the review exit 4 (incomplete) rather than 0. Tool-executing checks run only when the installed dependencies are compatible with the reviewed version's effective dependency graph, or when the profile opts in to `trust_installed_dependencies` for projects whose installation cannot be verified, with results clearly marked. In monorepos, roots that depend on a changed workspace package are type-checked and tested too.
- **Lazy impact graph**: Tree-sitter symbol tables for both versions, seed set from changed hunks, N-hop expansion through scope-filtered identifier search, base/head/delta slices written as JSON. LSP-backed reference resolution is an optional adapter capability not implemented by the v0.1 built-ins.
- **Findings and report**: a single finding model with evidence levels, stable identity `blake3(rule_id | normalized_location | trigger_hash)`, one finding per root cause with per-occurrence state, suppression application, and terminal, Markdown and JSON renderers. finding-v1 reserves the optional keys `round`, `first_posted_in` and `author_response` (`{ reason: fixed | wrong | intentional | irrelevant | style, actor, at, note }`) for review convergence and feedback; report-v1 carries `risk_tier: { tier, reasons[], source }` (null in v0.1 unless an `always_human` glob matches). `rio/prepare` reads `REVIEW.md`, `CLAUDE.md` and `AGENTS.md` per directory into an `owner_guidance.json` artifact in the run record; nothing consumes it in v0.1. The JSON document has a defined shape for every exit, including no changes, errors and interruption. The report ends with a footer of what could not be analyzed. Results are cached per review id and per run, with atomic publication, locking and crash-safe pruning, so concurrent reviews do not interfere. Tool processes are supervised as process groups (Job Objects on Windows), so cancellation leaves no workers behind.
- **Git and resource boundaries**: explicit behavior for conflicted indexes, shallow clones, submodules, Git LFS, sparse checkouts, symlinks and case-only renames; safe extraction, output and disk limits, user-only cache permissions and redaction of stored tool output.
- **Machine configuration**: `config.toml` keys for cache location, retention and size, parallelism and output limits, with flag > environment > file > default precedence; review behavior stays in profiles.
- **`rio doctor`** (local subset): reports detected languages, tool availability per adapter capability, profile validity, git state, dependency compatibility per root, cache writability and, through the same planner as `rio review`, which checks would run or be skipped and why.
- **Distribution**: a tag-triggered release workflow publishing archives for Linux (musl), macOS and Windows on x86_64 and arm64 with `SHA256SUMS` and build provenance attestations, published through a draft-verify-publish lifecycle in which release candidates never become latest, plus `install.sh` (POSIX `sh`, Linux and macOS) and `install.ps1` (Windows PowerShell 5.1 and PowerShell 7+) that verify checksums, stage and smoke-test the binary on the destination file system before replacing it, install without administrator rights, and uninstall with `--uninstall`/`-Uninstall`. The repository is licensed Apache-2.0.
- **Release acceptance**: the PRD exit criterion is recorded as an evaluation of 10 real pull requests in `docs/evaluation/v0.1.md`, with cold and warm p50/p95 timings, before `v0.1.0` is tagged.

Nothing is breaking: there is no prior behavior.

## Capabilities

### New Capabilities
- `cli/review`: the `rio review` command surface for local use: change selection flags, output formats and the JSON document for every exit, `--offline`, machine configuration, progress and partial-report behavior, exit codes from `fail_on` including 4 for incomplete reviews, run identity, and the explicit failure of endpoint-only flags.
- `cli/profile`: `rio profile list|show|validate` over repo, personal and built-in profile locations.
- `cli/doctor`: `rio doctor` diagnostics for the local pipeline: git state, adapter tool availability, profile validity, dependency compatibility, cache health and the check plan.
- `change-snapshot`: base and head resolution for working-tree, staged and `--base` modes; diff with hunk ranges; content-addressed snapshot pinned to immutable versions; repository-state and git-feature boundaries; safe materialization.
- `review-profiles`: profile schema v1 (including the reserved `posture`, `max_defects`, `rounds` and `always_human` keys), discovery order, inheritance, validation, built-in module resolution, guardrails, `suppress` and `fail_on`, and what the local engine executes versus defers.
- `language-adapters`: the adapter contract, capability declaration, repository detection, and the behavior of the built-in TypeScript, Python and Rust adapters.
- `deterministic-checks`: the five check kinds, their rule ids and finding types, check outcomes, occurrence-level base/head classification, dependency compatibility and trust, coverage eligibility, the OSV retrieval contract, and tool process lifecycle.
- `impact-graph`: lazy graph construction, node and edge model, confidence marking, slice output.
- `findings`: finding model (including the reserved `round`, `first_posted_in` and `author_response` keys), evidence levels, stable identity, root-cause grouping with per-occurrence state, regression states including `worsened`, suppression.
- `review-report`: terminal, Markdown and JSON rendering, report status, `risk_tier`, section order, ordering within sections, footer, the `owner_guidance.json` artifact, and the result cache with concurrency, recovery, retention and data-protection rules.
- `distribution`: release artifacts per target with checksums and provenance, the release publication lifecycle, the Unix `install.sh` and Windows `install.ps1` installers with staged replacement and uninstallation, and their download source override.

### Modified Capabilities
None. There are no existing specs.

## Impact

- **New code**: everything under `crates/`, `modules/`, `schemas/`, `scripts/install.sh`, `scripts/install.ps1`, the release workflow under `.github/workflows/`, and a `tests/fixtures/` directory with small TypeScript, Python and Rust sample repositories carrying seeded issues (`rs-sample` is a two-member Cargo workspace).
- **External tools invoked on the user's machine** (never bundled): `tsc`, `eslint`, `vitest`/`jest`, `c8`, `pyright` or `mypy`, `ruff`, `pytest`, `coverage`, `cargo` (`check`, `clippy`, `fmt`, `test`), `cargo-llvm-cov`. Each is optional; absence degrades to a `skipped` outcome with reason `tool_missing`.
- **Network**: OSV batch and per-advisory requests for the dependency audit, cached locally and disabled by `--offline`. No Rio backend, no model provider.
- **Dependencies** (Rust): `clap`, `serde`, `serde_yaml`, `serde_json`, `jsonschema`, `gix` (fallback `git2`), `blake3`, `fs4` (file locks), `ulid`, `tree-sitter` with the TypeScript, Python and Rust grammars (`tree-sitter-rust`), `cargo_metadata` or an equivalent `cargo metadata` JSON reader for workspace members and reverse dependencies, `toml` for `Cargo.lock` and `rust-toolchain.toml`, `tokio`, `reqwest`, `indicatif`, `globset`, `ignore`.
- **Contracts fixed for later changes**: profile schema v1 (including `fail_on`, which the TRD mentions but omits from its schema listing; this change adds it as a top-level key), module manifest v1, finding JSON v1, report JSON v1 with `status` and check outcomes, exit codes, `config.toml` keys, snapshot format, cache layout. v0.2 extends these; it must not break them. Keys added to the v1 schemas by this change for later consumers, all optional with defaults so existing documents stay valid: profile-v1 `posture`, `max_defects`, `rounds` (`cap`, `diff_only_after`), `always_human`; finding-v1 `round`, `first_posted_in`, `author_response`; report-v1 `risk_tier`. Later changes extend these the same way, always with optional keys: rio-v0-2-verifier adds profile-v1 `verify` (`voters`, `quorum`, `model`) and the `rio/security` step options, finding-v1 `verification`, and report-v1 `risk_tier.source: triage`; rio-v0-3-council adds profile-v1 `council`, module-v1 kind `member`, finding-v1 `council`, report-v1 council metrics, and the new `schemas/council-assessment-v1.json`; rio-v0-2-review-convergence adds no schema keys and consumes the reserved ones.
- **Deferred to later changes**: code signing and macOS notarization, Homebrew tap, `cargo install rio-cli` from crates.io, endpoint, `rio init`/`deploy`/`upgrade`, intent agent, agents, hypothesis board, verifier, consolidation across runs, PR mode, SARIF, feedback, `--since-last`, LSP reference resolution, third-party module registry, GitHub Actions runner, consumption of `posture`, `max_defects`, `rounds`, `author_response` and owner guidance (rio-v0-2-review-convergence, rio-v0-2-verifier), the council step (rio-v0-3-council).
