# Browser QA evaluation

This suite uses `tests/fixtures/qa-sample` and its committed `REVIEW.md`. Each case
starts from a clean Git repository, enables only its labeled defect/friction
variant, and runs all journeys in real mobile/desktop and light/dark cells.
Synthetic persona credentials are generated by the driver. The application
Dockerfile provisions dependencies; no package install runs on the host.

Build the current CLI and paired QA image, then use a local Codex subscription or
`RIO_QA_MODEL_ROUTE` configured for the host keychain relay:

```sh
cargo build -p rio-cli
docker build -f worker/Dockerfile.qa -t rio-qa:0.1.0 .
python3 eval/qa/run.py --local --harness codex --output /tmp/qa-codex
python3 eval/qa/run.py --local --harness pi --output /tmp/qa-pi
```

These are real model runs subject to QA wall/token budgets. Pi requires the host
model route. Every case has its own review budget; running the entire suite spends
across multiple reviews. `--case missing-confirmation --case clean` selects a
smaller acceptance run. `--rio PATH` selects a built binary. Local mode ignores
saved endpoint configuration; it does not publish or claim hosted verification.

Reports, sanitized command diagnostics, browser evidence cache and a checkpointed
`summary.json` are retained in the output directory. Recompute scores without
models using `--reports /tmp/qa-codex --output /tmp/qa-rescore`. Missing reports,
unavailable QA or zero completed cells exit 2. Every missing detection remains a
miss, including when the run is partial. A clean case's noise count includes both
unexpected observations and recommendations.
Fixture copy or Git setup failures are recorded as `fixture_setup_failed` with
zero coverage, and the driver continues to later cases. No QA report is invented
for a fixture that never started; machine-specific Git output is not retained.

`rule_match_precision` and `rule_match_recall` match labeled rule/journey pairs;
they are detection signals requiring human adjudication, not validated quality
claims. A matching observation can still be wrong. Verified and local unverified
matches are reported separately. Unexpected observations are review candidates,
not automatically proven false positives. Token cost, dollars and wall time come
from the actual report; unknown values remain null. `CASE.metrics.json` retains
measured browser cost for each chain × viewport × color scheme, read from the
exact run record named by the report, including nested baseline measurements when
a comparison ran. The `version` distinguishes base and head cells. It includes reset, retries and cleanup;
initial app/seed provisioning and verification remain run-level overhead. Shared
prerequisite/dependent chains are counted once. Token reservations used after an
interrupted provider response are marked estimated; subscription tokens and
unavailable dollar pricing remain null. Older reports without these records have
no measured per-cell metrics. Each executed cell's measurement is checkpointed
before the next cell starts, so later controller or cleanup failures retain the
completed measurements. Unstarted cells have no fabricated measurements.
Aggregate averages remain explicitly labeled.

UX recommendation assessment is independent of defect detection. The duplicate
address case must still complete checkout. The ambiguous action, lost-input,
missing cancel and keyboard barrier cases test goal clarity, recovery, control
and inclusive interaction. Intentional brand styling and the clean flow check
whether advice respects owner exceptions. For every recommendation, a reviewer
must score `guidance_adherence`, `relevance`, `actionability` (0–2: absent, partial,
clear), and `unsupported_benefit_claim` (true/false). Inspect the retained evidence
and cite it in review notes. A supported recommendation establishes friction and
proposal relevance; it does not demonstrate the proposed benefit. The driver
leaves these fields null rather than inferring human judgments from wording.

Supply completed human assessments with `--labels PATH` when running or rescoring:

```sh
python3 eval/qa/run.py --reports /tmp/qa-codex --output /tmp/qa-rescore \
  --labels docs/evaluation/v0.3-qa-human-labels.json
```

The version 1 JSON document has a `labels` array. Each label names the immutable
`run_id`, recommendation `id`, `reviewer`, and `evidence_notes`, together with the
three integer scores and boolean `unsupported_benefit_claim`. A label applies
only to that run and recommendation; it never carries forward to a later run
with the same stable recommendation ID. Invalid or duplicate labels fail
validation. Unlabeled recommendations remain pending. The separate `ux_metrics`
reports human label coverage, mean scores, and unsupported-benefit claim count;
it does not change defect precision/recall or imply demonstrated user benefit.

## UX review hillclimb

`hillclimb.py` runs the non-defect cases as focused mobile/light journeys and grades the model-authored review with
`judge.py`, a Claude judge called through the AI Gateway (`gateway_client.py`). The judge compares each recommendation and
unverified observation with grader-only ground truth in `frictions.json`; never copy that file into the fixture or a prompt.
Cases with `focus_journey` select their journey; the original focused cases use the mapping in the runner. Results are written under `--flow`
(`results.jsonl`, `traces/`, `reports/`, `judge/`, `stderr/`) and are machine-local; do not commit them. A run with a QA report is
graded even when its cell was cancelled; only runs without a report are retried. `--regrade` re-judges stored reports without
new QA runs. Install its pinned dependency with `pip install -r eval/qa/requirements.txt` in a virtualenv. See
[the hillclimb record](../../docs/evaluation/v0.3-qa-ux-hillclimb.md).
