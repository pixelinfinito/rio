# v0.2 verifier comparison: candidate reference cases

**Status: draft candidate set. Not preregistered, not adjudicated, not run.**
Prepared on 2026-11-06 for task 1.1 of
[`rio-v0-2-review-convergence`](../../openspec/changes/rio-v0-2-review-convergence/tasks.md).
Selection used public GitHub data only, through the authenticated `gh` CLI and
shallow clones. No Rio review ran and no model API was called. Every label below
is a **proposed** label from automated research (`verdict_source: automated`).
The user's team must confirm each label independently before any live run (see
[adjudication](#independent-adjudication-still-required)).

## Purpose and mapping to the comparison gates

`python3 -I eval/verifier.py` compares a single-verifier arm (`verify.voters: 1`)
with the three-voter quorum on identical pinned cases. It accepts v0.2 only when
every gate in [eval/README.md](../../eval/README.md#v02-verifier-comparison-pinned-acceptance)
passes. This set feeds those gates as follows:

| Gate | What this set supplies |
| --- | --- |
| The reference set has known high-severity issues **and** independently clean controls | 12 high-severity positive controls (`HS-*`) and 12 clean controls (`CL-*`), each about four per language. |
| Quorum precision ≥ 0.80 | Findings on both groups go into precision. Clean controls are the main source of false-positive pressure. On positive controls, findings other than the registered defect still need individual verdicts. |
| High-severity recall not below the single-verifier baseline | Each `HS-*` case registers exactly one `high_controls` ID (the case ID in lower case, e.g. `hs-py-01`). The harness fails when the single arm detects a control that the quorum misses (`lost_high_controls`). |
| Complete data, `execution: live-model` | Out of scope here. Both arms must produce a report, an endpoint audit and verdicts for every case. |

Manifest mapping (schema [`verifier-manifest-v1`](../../eval/schema/verifier-manifest-v1.json)):

- `HS-*`: `high_controls: ["hs-…"]`, `independently_clean: false`.
- `CL-*`: `high_controls: []`, `independently_clean: true`. Set this only after an
  independent clean assessment. The 90-day selection rule below is necessary
  evidence, not sufficient evidence.
- `generator_model`, `voter_model` and `profile_hash` are the same for every case
  and come from the deployed pinned `rio/openrouter` profile.

## Selection criteria actually applied

Applied to every case:

- Public GitHub repository with a permissive licence, checked through the GitHub
  API: MIT, Apache-2.0, MIT/Apache-2.0 dual or BSD-3-Clause. For `withastro/astro`
  the API reports `NOASSERTION`, but the root `LICENSE` file is MIT.
- Languages Rio reviews: Python, TypeScript/JavaScript and Rust, about four per
  language in each group.
- No more than 3 cases from one repository across both groups (the maximum used
  is 2).
- No reuse of earlier evaluations. A grep of `docs/evaluation/` and `eval/` (1,068
  PR URLs across 52 repositories) found no overlap with any repository used here.
- The introducing PR, fix PR and clean PR numbers, merge state, merge commits and
  line counts were read from `gh pr view`. Sizes are the additions/deletions that
  GitHub reports for the whole PR, including tests and changelogs.

Positive controls (`HS-*`):

1. A merged PR introduced the defect, and a later merged PR fixed it or reverted
   the offending part.
2. The link between them was verified in one of two ways: the fix PR or its
   issue names the introducing PR or commit, or (for HS-RS-01 only) a GraphQL
   blame of the fix's parent attributes the lines to the introducing PR. In every
   case `gh pr diff` showed that the line the fix changes was added by the
   introducing PR.
3. Consequence category: crash or panic, data corruption, broken security or
   TLS behaviour, wrong results, or an unbounded memory leak. Defects that are
   only style or performance issues were rejected (examples: pytest #13338,
   svelte #16270, black #3564).
4. Introducing PRs of 8–542 changed lines were preferred. All twelve are under
   600 lines.

Clean controls (`CL-*`):

1. Selected with the repository's own selector,
   `python3 -I eval/noise.py select --repo CLONE --branch BRANCH --now 2026-11-06T00:00:00Z --since 2026-02-01|2026-04-01`
   (some runs added `--pr` filters), on shallow clones of the default branch
   (since 2026-01-15 or 2026-03-01; full clones for clap and preact). `status: clean`
   means:
   - it is a merged PR (squash or merge commit);
   - no later revert was found;
   - no later first-parent commit edits, or inserts next to, any of its hunks
     within 90 days, with ranges carried through the commits in between;
   - its 90-day window has fully elapsed.
2. The PR also had to change non-test Python/TS/JS/Rust source and have a
   behaviour-bearing title (fix or feature, not docs, typos or dependency bumps).
3. Each was cross-checked with `gh pr view` for merge commit and size.

Rejected during selection: `aio-libs/aiohttp` clean candidates (all 8 tried were
excluded because changelog/`CONTRIBUTORS.txt` hunks were touched within 90 days)
and `rust-lang/cargo` (the selector found no PR subjects in the shallow history).
Runs for `vitejs/vite`, `nodejs/undici` and `astral-sh/uv` did not finish in time
and were stopped.

## Known risks

- **External-context defects.** Several positive controls need knowledge outside
  the diff hunk, so a miss in both arms says little about the verifier:
  - HS-PY-01 (`CancelledError` is a `BaseException`);
  - HS-PY-02 (cryptography raises `TypeError` for a password on an unencrypted
    key);
  - HS-PY-03 (truststore or system CA behaviour);
  - HS-TS-03 (`@cloudflare/vite-plugin` merges the customizer output);
  - HS-RS-01 (`open_rw_exclusive_create` does not truncate; it lives in
    `flock.rs`);
  - HS-RS-03 (`Cache` drop semantics).

  HS-RS-02, HS-RS-04 and HS-TS-01 are visible within the hunk.
- **The recall gate is relative.** The harness fails only on controls the single
  arm detects and the quorum misses. If both arms miss most controls, the gate
  still passes. Report absolute per-arm detection alongside it, and consider
  agreeing a minimum before the run.
- **Severity is arguable for some cases.** HS-PY-02 never shipped. HS-TS-02
  affects only the meta-refresh body (the `Location` header is correct).
  HS-RS-04 needs a specific flag combination. HS-TS-03 needs user KV bindings
  plus sessions. Adjudicators may downgrade these, and an `HS-*` downgraded to
  medium should be dropped from `high_controls`, not kept.
- **Unreleased or nightly-only defects.** HS-PY-02, HS-RS-02 and HS-RS-04 were
  fixed within days of introduction. They are real merged defects, but impact
  claims rest on maintainer and issue text.
- **Flaky or heavy reproductions.**
  - HS-TS-04 (HTTP/2 abort timing and leak measurement) and HS-PY-01
    (cancellation timing) depend on asyncio or socket timing.
  - HS-TS-02 needs a Nuxt fixture build.
  - HS-PY-03 needs a custom-CA environment.
  - HS-RS-02 and HS-RS-03 have no regression tests in their fixes.

  None of these reproductions has been run.
- **Large and partly unrelated diffs.** HS-PY-04 (+458), HS-RS-02 (+483) and
  HS-RS-03 (11 files) contain much unrelated code. That increases the chance of
  findings unrelated to the control, each of which needs its own verdict.
- **Clean-control limits.**
  - The selector checks only first-parent commits on the default branch within
    90 days. It does not see backport-branch fixes, issues reported but not yet
    fixed, or defects fixed later by a commit that does not touch the same hunk.
  - Clean PRs are smaller (14–311 changed lines; median about 90) than positives
    (8–542; median about 155). This can bias precision upward on clean controls.
  - Shallow clones mean revert detection covers only commits inside the clone.
  - The fastapi run was `--pr`-restricted.
- **Correlated cases.** Two cases come from each of nuxt, cargo, fastapi,
  urllib3, h3, tokio and clap. Report per-repository results; these are not
  24 independent samples.
- **Language mix.** In the TS/JS group, HS-TS-04 and CL-TS-04 are JavaScript; the
  other six are TypeScript.

## Independent adjudication still required

Before any live run, the user's team must record, for every case and with a
named reviewer (`verdict_source: human` if the PRD's human confirmation is to be
claimed):

1. **Positive label.** Confirm that the defect exists at the pinned head, that
   the introducing PR is the cause (not only the place where it surfaced), and
   that it is high severity. Ideally run the fix's regression test at the
   introducing head and at its base. Write the control ID, mechanism and
   evidence into the verdicts file before seeing Rio output.
2. **Clean label.** Independently assess each `CL-*` diff as introducing no
   defect: read the code, check the issue tracker for reports after merge, and
   run the PR's tests. Only then set `independently_clean: true`.
3. **Expected location.** Agree on what counts as detecting each control: file
   plus symbol, and whether a finding at the enclosing function but with a
   different explanation counts. Record this so `control_id` attribution in the
   verdicts is not decided after the fact.
4. **Per-finding verdicts after the run.** Assign each finding in both arms
   true-positive or false-positive with artifact-backed evidence. Use the same
   reviewer protocol for both arms, and if possible keep reviewers blind to
   which arm produced the finding.
5. **Recorded exclusions.** Record any case dropped or swapped (for example
   for a reserve) with its reason, and do not drop a case after seeing Rio
   output.
