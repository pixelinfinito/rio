# v0.3 PR mode: live acceptance on a test account

Task 10.4 of `openspec/changes/rio-v0-3-core`: install the GitHub App on a test repository, open a pull request, observe the review and its publication, run `rio review --pr` and `rio suppressions apply` against it, and record the evidence here. Everything up to the app's registration is implemented and tested against recorded GitHub doubles (see the stage 4 validation record in `tasks.md`); the steps below need the endpoint owner, because creating a GitHub App is a browser confirmation on the owner's GitHub account and the test repository is theirs.

**Status: not run.** Nothing was created on any GitHub account. The record section at the end is empty until the owner runs these steps.

## Before you start

- A GitHub account or organization for the test, and a test repository in it that you can push to (a fresh private repository is enough). For the fork scenario, a second GitHub account that can fork it.
- The endpoint's model credit: each review with `rio/openrouter` models costs about USD 0.5 to 1.3. The steps below run about six reviews; keep the total under USD 10.
- Docker, the Cloudflare `cf` CLI logged in (`cf auth whoami`), and this branch checked out.
- The Sandbox backend prepares same-repository pull requests only. Fork pull requests need the self-hosted runner (`rio-runner serve`, step 10); on a Sandbox-only endpoint a fork PR is recorded as `fork_requires_self_hosted_runner` and nothing is posted, which is itself a scenario to observe.

## Rehearsal against the recorded doubles (no account needed)

```sh
~/.cargo/bin/cargo test -p rio-cli --bin rio github_app          # manifest flow, secrets, rotation
~/.cargo/bin/cargo test -p rio-cli --test cli -- pull_request doctor_reports hosted_prepare
cd worker && npx vitest run tests/github-app.test.ts tests/pulls.test.ts tests/publish.test.ts tests/pr-mode.test.ts
RIO_TEST_DOCKER=1 RIO_RUNNER_IMAGE=rio-runner:0.3.0 python3 -m unittest worker.runner.tests.test_docker_runner -v
```

`registration_stores_the_secrets_on_the_worker_and_nothing_secret_on_disk` runs `rio init`'s GitHub App step end to end against a GitHub and Cloudflare double: the loopback page, GitHub's redirect with a forged and then the real `state`, the code conversion, the three Worker secrets, and a `config.toml` that holds no secret. `worker/tests/pr-mode.test.ts` drives a whole PR lineage through the Worker's own entry points.

## Steps

1. **Build** from this branch (the CLI embeds the Worker bundle; the runner image ships `rio`, git and the toolchains):

   ```sh
   (cd worker && npm ci && npm run bundle)
   ~/.cargo/bin/cargo build --release --locked -p rio-cli -p rio-runner
   docker build -f worker/Dockerfile -t rio-runner:0.3.0 .
   ```

2. **Deploy and register the app.** `rio init` redeploys the endpoint (migration `0006_pull_requests.sql` is applied) and then runs the GitHub App step:

   ```sh
   ./target/release/rio init --runner-image rio-runner:0.3.0 --credential-store file --github-app
   # or, for an organization: ... --github-app --github-org <org>
   ```

   A browser opens `http://127.0.0.1:<port>/`, which continues to GitHub's "Create GitHub App" page with the manifest. Observe on that page: the name `Rio review <endpoint host>`, webhook URL `https://<endpoint>/v1/hooks/github`, and exactly the permissions Contents read, Pull requests read & write, Checks read & write, Metadata read, Members read, with the Pull request and Issue comment events. Confirm. The terminal prints the app id, slug and installation URL. Check that `~/.config/rio/config.toml` has a `[github_app]` table with `app_id`, `slug` and `installation_url` only, and that no file under `~/.config/rio` contains `PRIVATE KEY` (`grep -rl "PRIVATE KEY" ~/.config/rio` prints nothing).

3. **Install** the app with the printed URL on the test repository only ("Only select repositories").

4. **Opt the repository in.** On the test repository's default branch, add `.rio/profiles/default.yaml` and push it (the endpoint uses the profile at a pull request's merge base, so it must be on the base branch):

   ```yaml
   version: 1
   name: pr-mode-acceptance
   extends: rio/openrouter
   publish: auto
   ```

   For step 9 it helps if one dismissal proposes a suppression: a child's `steps` replaces the inherited list, so copy the `steps` that `rio profile show rio/openrouter` prints into this file and change the report step to `with: { class_threshold: 3, proposal_threshold: 1 }`; validate with `rio profile validate`. Then, in a local clone, run `rio doctor` and observe the endpoint lines: `paired: true`, `github_app: {configured: true, installed: true}`, `publish_policy` of your local default profile, and no installation warning. Optionally run `rio doctor` in a clone of a repository the app is not installed on and observe the warning with the install URL and exit code 0.

5. **Open a pull request** that introduces a defect an agent can prove, for example a function that now throws on a path its callers use. Observe within a few minutes, and record the URLs:
   - a `rio/review` check run on the head commit, conclusion **neutral**, titled with the status, counts and risk tier;
   - one inline review comment per finding on a changed line, ending with a hidden `<!-- rio:finding:<64 hex> -->` marker (view the comment's source);
   - one summary comment with the risk tier, counts, any findings outside the diff and the report link, ending with `<!-- rio:summary:<64 hex> -->`;
   - nothing for a draft PR until "Ready for review".

6. **Push a second commit** that fixes one finding. Observe: no new inline comment, the fixed finding's comment edited to "Status: fixed in `<sha>`" with its thread resolved, the same summary comment edited, and a new neutral check run on the new head.

7. **Dismiss a finding** as a collaborator: comment `/rio dismiss <first 8+ characters of its id> intentional documented behavior`. Observe a 👍 reaction, the finding's comment edited to "Status: dismissed: intentional (by <login>)" and its thread resolved. Comment `/rio dismiss abc style` and observe a 👎 reaction and no change. From an account without write access, observe 👎 for `/rio review`.

8. **Run the CLI** in the clone:

   ```sh
   ./target/release/rio review --pr <n>                 # report rendered; publication footer
   ./target/release/rio review --pr <n> --format sarif > pr.sarif
   ```

   Observe that local uncommitted edits do not appear in the report, the header shows `Pull request: <owner>/<repo>#<n>` with the head SHA, and the exit code follows the report (1 with a failing finding). Then set `publish: ask` on the base branch, push a commit to the PR, observe that the webhook review posts only the check run with the summary naming `publish: auto` and `rio review --pr <n> --publish`, and run `rio review --pr <n> --publish` to publish it.

9. **Suppression proposal.** Dismiss a finding with reason `style` (`/rio dismiss <id> style`), let a new review finish (push a commit), then:

   ```sh
   ./target/release/rio suppressions list
   ./target/release/rio suppressions apply <id>
   ```

   Observe the proposal with its evidence, the confirmation prompt, and the entry appended to `.rio/profiles/default.yaml`.

10. **Fork pull request** (optional on a Sandbox endpoint). From the second account, fork and open a PR. On a Sandbox-only endpoint, observe that `rio review --pr <fork n>` reports `fork_requires_self_hosted_runner` and nothing is posted. With a self-hosted runner (`RIO_RUNNER_SECRET=<RUNNER_SECRET> ./target/release/rio-runner serve --endpoint https://<endpoint> --image rio-runner:0.3.0` on a Docker host, after `rio deploy --runner self-hosted`), observe the review runs static-only and posts nothing; comment `/rio review` as a maintainer and observe the review is published with the footer's static-only line.

11. **Rotate the webhook secret:** `./target/release/rio doctor --rotate`. Observe "Webhook secret rotated", then push a commit and observe the next review still arrives.
