# v0.3 agent reference cases: candidate selection

**Status: selected and pinned; not adjudicated.** Prepared on 2026-11-07 for tasks 8.3
and 9.6 of [`rio-v0-3-core`](../../openspec/changes/rio-v0-3-core/tasks.md). Selection
used public GitHub data only (authenticated `gh` CLI, file reads at the pinned commits,
shallow clones for the clean-control selector). Every label below is a **proposed**
label from automated research (`verdict_source: automated`); the owner's independent
adjudication is still required (see [v0.3-agents.md](v0.3-agents.md)). Candidate data
(JSON with every expected location), selector outputs and file snapshots are kept
privately on the maintainer machine under `~/rio-v03-agents-run/selection/`.

## Purpose

The contracts agent (`contracts/<kind>/<break>` hypotheses) and the security agent
(catalog-item hypotheses) are measured separately from the correctness agent. This set
gives each agent at least four positive controls, each a real merged PR that introduced
the problem and a later PR that fixed or reverted it, plus two clean controls on which
any finding needs its own verdict. The primary set is 13 cases: CT-POS-01..05,
CT-CL-01..02, SE-POS-01..04 and SE-CL-01..02. Reserves are listed but were not run.

Each positive is captured as an eval case under
[`eval/cases/v0.3-agents/`](../../eval/cases/v0.3-agents/) (schema
[`eval-case-v1`](../../schemas/eval-case-v1.json)). The control is registered at file
plus symbol, with the expected detecting agent in `expected[].agent`. Clean controls
have no eval case (the schema needs at least one expectation); they are clean cases in
the run manifest. Expected locations were written from this selection before the live
run and were not changed afterwards.

### Criteria actually applied

Positives:

1. Public repository with a permissive licence read from the GitHub API (MIT,
   Apache-2.0; foundry is MIT/Apache-2.0 dual, API reports Apache-2.0).
2. Language TS/JS, Python or Rust. The five primaries are 2 TS/JS, 2 Python, 1 Rust.
3. Tracked files counted from the recursive git tree at the pinned head: no
   submodules, no `filter=lfs` in `.gitattributes`. All under 5,000 except polar
   (5,222, kept and flagged).
4. Introducing PR merged, 8–600 changed lines as reported by GitHub (range used:
   11–375).
5. A later merged fix or revert. Link verified both ways for every row: the fix
   PR, its revert commit message or its linked issue names the introducing PR or
   commit, **and** `gh pr diff` of the fix touches lines that the introducing PR
   added or removed.
6. The consumer was found by reading files at the pinned head: an import scan for
   vellum, `grep` for slime, foundry and focus-trap-react, and the spec JSON for
   polar. Symbols and line numbers were read from file contents at the stated
   version (`base` for removed code, `head` otherwise).
7. Contract namespace `contracts/<kind>/<break>`. Cases with only external
   consumers are marked `consumer_in_repo: false` (a "risk" expectation).
8. No repository listed in `docs/evaluation/` was used. Repositories cloned by the
   sibling security selection (`sec-*` clones: uvicorn, werkzeug, express, koa
   and others) were also avoided.

Clean controls:

- Selector `status: clean`, as above.
- A behaviour-bearing change to a public API surface (an exported option type or
  a config default).
- Manually checked to be additive or widening, and **not** a removal, rename or
  positional reordering. That check rejected four selector-clean PRs; see below.

### Known risks and open items

- **Not adjudicated.** Every label is a proposed label from automated research.
  The clean rows still need an independent clean assessment.
- **Out-of-diff consumers.** CT-POS-01 and CT-POS-02 have their consumer outside
  the changed files, so the agent must search importers or readers in the
  snapshot. CT-POS-04's consumer sits inside ~97k-line generated JSON files.
- **Risk-only cases.** CT-POS-05, CT-RES-01 and CT-RES-02 depend on consumers
  outside the repository. A miss there is weaker evidence than a miss on
  CT-POS-01 to CT-POS-04.
- **Extra unregistered contract change in CT-POS-04.**
  `BenefitDiscordCreateProperties.guild_token` → `guild_id` breaks the request
  schema in the same specs, and the fix deliberately did not restore it. A finding
  there should be judged on its own, not counted as a false positive by default.
- **Unverified sub-claims** are listed per row in `contracts.json` (`unverified`).
  The main ones:
  - slime: the revert gives no reason, and the runtime `AttributeError` was not
    executed.
  - foundry: whether `-f` was ever restored is unknown.
  - Breakage reproductions were not run for any row (no `tsc`, SDK or hosting
    tests).

One-line vulnerabilities:

- **SE-POS-01**: the new Tailscale Ping monitor runs `exec(`tailscale ping ${hostname}`)` with the user-set
  hostname. The only validation is a front-end `pattern` attribute, so this is authenticated OS command injection.
- **SE-POS-02**: moving glob options into a config field flipped the Unix default to
  `require_literal_leading_dot = false`, so `$HOME/*` scopes now allow `~/.ssh`. The new comment
  ("dotfiles are not supposed to be exposed by default on unix") contradicts the code.
- **SE-POS-03**: in a "typing chore", `isinstance(issuer, list)` became `isinstance(issuer, Sequence)`. A `str`
  issuer is now compared with `in` (substring), so `iss: "urn:"` passes for `issuer="urn:expected"`.
- **SE-POS-04**: the new `getPushExample` socket handler has no `checkLogin` and does
  `path.join("./extra/push-examples", language)`. An unauthenticated client can traverse directories and read `index.*` files.
- **SE-POS-R1**: in code position only the leading `<` of a `</script…>` match is neutralised. A `[^>]*` match
  can swallow a second complete `</script>`, which is then emitted raw (XSS).
- **SE-POS-R2**: `Hint::monotonic` was relaxed from `<` to `<=` for both cuts and indices, so ML-DSA
  signatures with repeated hint indices are accepted (malleability).

### Criteria actually applied

Positives:

1. Public GitHub repository with a permissive licence, checked through the API and, where the API was
   ambiguous, the licence file at the pin: MIT, Apache-2.0/MIT dual, or BSD-3-Clause. Languages:
   TypeScript/JavaScript, Python or Rust. Mix: 2 JS, 1 Rust, 1 Python among the primary positives;
   reserves are 1 JS and 1 Rust.
2. Small-to-medium repository: 12-806 tracked files, counted from the GitHub git tree at the head pin.
   No `.gitmodules` or `.gitattributes` (no submodules or LFS) in any pinned tree.
3. A merged PR introduced the defect, and a later merged PR or commit fixed it. Every case has a GHSA.
   Five of the six also have a CVE; GHSA-hfxh has none and GHSA-5px6 is a repository-only advisory.
4. The link was verified as follows. The advisory names the introducing commit or PR (PyJWT, Tauri,
   serialize-javascript, ML-DSA), or quotes the vulnerable code at a path that the introducing PR created
   (both uptime-kuma cases). In every case `gh pr diff` showed the vulnerable line added, or the protection
   removed, by the introducing PR. The fix changes those same lines. The release containing the introducing
   commit matches the advisory's affected range (GitHub compare API).
5. Size: 8-600 changed lines (actual range 25-272).
6. Pins: head is the squash-merge commit and base its only parent, both read with `gh api commits` and
   full length. The expected locations were read from files at the pinned commits
   (`gh api contents?ref=SHA`; snapshots are in `security-evidence/`).
7. No repository listed anywhere in `docs/evaluation/` (or in `eval/`) is used. No repository supplies
   more than 2 cases; uptime-kuma supplies 2 positives (SE-POS-01 and SE-POS-04), which are correlated.

Clean controls:

1. Selected with
   `python3 -I eval/noise.py select --repo CLONE --branch BRANCH --now 2026-11-07T00:00:00Z --since 2026-03-01`
   on shallow clones (`--shallow-since=2026-01-01`). All three chosen PRs have `status: clean` and
   `kind: squash`, and base/head match the selector output. The selector's policy: merged, no later revert,
   no later first-parent commit editing or inserting next to its hunks within 90 days, and the window
   has fully elapsed.
2. The PR must change security-relevant non-test source with a behaviour-bearing title: token verification,
   header-name validation, or Content-Length parsing.
3. Repository advisories were listed (none after the PR's merge). Issues filed after the merge were
   searched by keyword (jsonwebtoken, koa). Recent file history was read in the clone.

### Known limitations and open items

- **Not adjudicated.** No reproductions or regression tests were run for any case. Clean labels rest on the
  selector, advisory lists and limited issue searches; each needs an independent human clean assessment
  before `independently_clean: true`.
- **Expected locations for missing checks.** For SE-POS-04 the `removed_check` entry points to where the
  check is absent (a new handler), not to deleted lines. Adjudicators should agree whether a finding at
  the `getPushExample` handler that cites only traversal, or only the missing login, counts as detection.
- **Difficulty spread.** SE-POS-01 and SE-POS-04 are textbook. SE-POS-02 and SE-POS-03 need the reviewer to
  reason about semantics: a flipped default, and `str` being a `Sequence`. The reserves are hard.
- **Correlation.** The two uptime-kuma positives come from the same repository and era (2023, v1.23/v2-beta).
- **Size bias.** The clean controls (38-67 changed lines) are smaller than the positives (25-272).
- **Catalog mapping is a proposal.** Alternatives: SE-POS-03 V9.1; SE-POS-04 V8.3; SE-POS-R1 V3.2.
