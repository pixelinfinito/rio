# v0.3 change sequence

v0.3 is specified as four OpenSpec changes. This document fixes the order in which they are implemented and archived, what each stage delivers on its own, and which spec deltas overlap so that archiving in the wrong order loses requirements. The PRD's v0.3 exit criteria are "false positives per agent < 15 %" and "the council beats the verifier-only baseline on the `plausible` bucket or is removed".

| `rio-v0-3-core` | R13, R14, R15, R16, R17, R18, R29 | Stage 2 (groups 0, 8, 9, 10.1) merged 2026-11-08 in PR #7 and its deltas synced to main; stages 3 and 4 open |

## Stages

Each stage ends with its tasks' verification, the hosted CI matrix and, where listed, a live acceptance record. A stage may start while the previous one's live acceptance is pending, but not before its code has merged.

### Stage 1. Close v0.2: `rio-v0-2-review-convergence`

Done. Task 8.3 (the nightly noise schedule) was finished and the change archived on 2026-11-07; its deltas are main specs, which every later change consumes (lineages, `findings` table, lifecycle status, feedback endpoint, eval aggregations). Task 1.1, the pinned quorum-versus-single-verifier comparison, closed on 2026-11-08: the first live run failed before any model call (fixed in PR #5), the second ran both arms on 23 of 24 cases with further fixes along the way (PRs #8 and #11), and the owner accepted it, adjudicating every agent finding as a true positive. The owner also decided that reviews which are incomplete only because the hosted runner skipped deterministic checks are scorable, rather than adding the tools to the runner image.

Delivers: v0.2 acceptance evidence (owner-adjudicated); the `wrong`-per-agent aggregation that the v0.3 false-positive gate reads.

### Stage 2. `rio-v0-3-core`, part A: agents and catalogs (task groups 0, 8, 9, 10.1)

Contracts agent, security agent with the OWASP and ASVS catalogs, the `security` community profile, the schema and migration groundwork for the rest of the change, and the false-positive release gate. No external service is involved, so this is the cheapest part to ship and evaluate, and it unblocks the council (which is enabled in the `security` profile) and the eval reference set growth.

Delivers: R13 and R29; the v0.2 "security unavailable" note disappears; per-agent precision measured for five agents.

Done 2026-11-08 (PR #7). The reference run of 13 real cases (`docs/evaluation/v0.3-agents.md`) detected 4 of 5 contracts controls and 4 of 4 security controls with no finding on the clean controls; the owner accepted the run and adjudicated every agent finding as a true positive, so the recorded precision is owner-adjudicated, not independent. The delivered capabilities are main specs; the remaining deltas (PR mode, finding history, SARIF, suppression proposals, agent cache) stay in the change.

### Stage 3. `rio-v0-3-core`, part B: local and endpoint features (task groups 4, 5, 6, 7)

Finding history, SARIF, suppression proposals and the agent result cache. All work with the CLI and endpoint only; none needs GitHub. SARIF and finding history are what CI integrations consume, so shipping them before PR mode lets teams wire Rio into code scanning uploads while the app is being built.

Delivers: R15, R16, R17, R18.

### Stage 4. `rio-v0-3-core`, part C: GitHub App and PR mode (task groups 1, 2, 3, 10.2–10.4)

App registration at `rio init`, webhooks, hosted preparation on the runners, the publisher and `rio review --pr`. This is the only stage that talks to an external service and the one with the live acceptance record on a test account. The convergence rules that stage 1 archived become visible on PR threads here. Archive `rio-v0-3-core` after 10.4.

Delivers: R14 and the PR-thread half of R27 and R28.

### Stage 5. `rio-v0-3-council`

Can start after stage 2 (it needs the `security` profile and the security agent's `plausible` findings to have something to council) and run in parallel with stages 3 and 4. Its author-family rule reads PR metadata from stage 4 and reports "not applicable" until then; its `nightly` trigger reads the schedule from stage 1. The A/B against verifier-only (task 7.3) decides whether the step stays; archive with the verdict recorded.

Delivers: R30 and the second v0.3 exit criterion.

### Stage 6. `rio-v0-3-qa`

Independent of the council and of stage 3. Its task group 7a (PR publishing of QA findings) is gated on stage 4's publisher and must be implemented against the archived `pr-publishing` capability, not re-specified. Its task 0.5 composes its finding-model and footer deltas with the convergence and core changes. Because it is the largest change and needs the QA runner image and pod isolation, it is scheduled last; a team that wants it earlier can start groups 0–6 after stage 2 and hold 7a for stage 4.

Delivers: R32, the first behavior-level review.

## Spec deltas that overlap

Three changes modify the same main-spec requirements. `openspec archive` writes a MODIFIED block whole, so the change archived last must carry every earlier addition; each change has a composition task that checks this (`rio-v0-3-core` 0.5, `rio-v0-3-council` 0.7, `rio-v0-3-qa` 0.5).

| Requirement | Changes | Archive order |
| --- | --- | --- |
| `review-profiles` / Built-in step options | core, qa | core, then qa |
| `review-profiles` / Rule expressions are validated syntactically | council | council only |
| `review-report` / Footer content | convergence (via lineage lines), core, qa | convergence, core, qa |
| `review-report` / JSON renderer | core | core only |
| `review-report` / Section order | council, qa | qa, then council |
| `findings` / Finding model | convergence, qa | convergence, then qa |
| `findings` / Suppression application | core | core only |
| `cli/review` / Output format selection, Exit codes | core | core only |

The council and QA changes express most report additions as ADDED requirements; both still add their results section to `Section order`, the QA change extends `Finding model`, and the council extends `Rule expressions are validated syntactically` with its predicates.

`crates/rio-core/tests/documentation.rs` (`overlapping_deltas_carry_every_earlier_addition`) enforces this for the five composed requirements (`Rule expressions` by its predicate and action names, the others by clause or step): every active delta must carry the main spec's items, every archived delta's items must be in the main spec, and each later change in the archive order above must carry every earlier change's additions. A later change may miss an addition only while its own composition task is open; the test prints each such gap. The QA delta carries the convergence finding model and lineage footer plus the core step options and five additional footer clauses; task 0.5 verified that they survive composition. QA archived before the council, so the council's `Section order` delta carries the QA results section and places council results before it.

## Schema versions

All four changes extend the v1 contracts with optional keys only. The additions, in archive order:

1. convergence: finding-v1 `status`, `resolution`; report-v1 `lineage`.
2. core: finding-v1 `history`, `source.cached`; report-v1 `publication`, `cache`, `suppression_proposals`; module-v1 kind `catalog`; profile-v1 `publish` semantics, `rio/agents.cache`, `rio/report.proposal_threshold`.
3. council: profile-v1 `council`; module-v1 kind `member`; finding-v1 `council`; report-v1 `council`; new `council-assessment-v1`.
4. qa: finding-v1 category `ux`, `qa`, occurrence `cell`; report-v1 `qa`; module-v1 kind `ruleset`; profile-v1 `budget.<mode>.qa`; new `journey-v1`, `qa-config-v1`, `qa-seed-v1`, `qa-fixtures-v1`, `qa-replay-v1`.

A CLI from stage N must keep reading reports from stage N+1 endpoints; the version pairing check only rejects protocol changes, and none are planned.

## Exit criteria mapping

| Criterion | Measured by | Stage |
| --- | --- | --- |
| False positives per agent < 15 % | `eval/gate.py --false-positive-rate` over `wrong` responses on the reference set and adjudicated noise runs | 2 (gate exists), 4 (PR responses flow in) |
| Council beats verifier-only or is removed | `eval/council.py` A/B on the `plausible` bucket, keep-or-remove rule in the release checklist | 5 |
| Precision ≥ 80 % (carried from v0.2) | convergence task 1.1: live comparison of 2026-11-08, owner-adjudicated 100 % in both arms | 1 |
| Harmful noise not above the previous release | nightly noise run and release gate | 1 onward |
